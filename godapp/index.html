genai-observability-data

A synthetic observability data generator that produces realistic distributed traces and structured logs for GenAI-powered systems, following the OpenTelemetry GenAI Semantic Conventions (semconv 1.41.0, experimental).

Use it to populate an OTel stack (Jaeger + Loki + Grafana + Prometheus) with representative data for dashboarding, alerting rule development, anomaly detection, or testing observability tooling against GenAI workloads - without needing a live production system.

god --traces 500 --scenario rag_meltdown --otlp http://localhost:4318
      |
      +-- ScenarioEngine   (time-bounded fault injection)
      |       |
      |       +-- ScenarioSpec (Pydantic config) + ScenarioHandler (stateless fault logic)
      |       +-- db_degradation / llm_latency_spike / provider_failover / ...
      |       +-- tool_call_timeout / memory_store_degradation / agent_bootstrap_failure / ...
      |
      +-- ServiceRegistry  (15-service topology with dependency graph)
      |
      +-- generate_dataset (Trace + LogEntry per virtual request)
      |       |
      |       +-- api-gateway root span
      |       +-- auth-service + postgres-auth
      |       +-- RAG path: embed -> vector-db -> llm-gemini (+ tool/MCP)
      |       +-- payments path: payments-service -> postgres-payments + kafka
      |       +-- agentic path: workflow-orchestrator -> agent-service -> llm + tools + memory
      |
      +-- Sinks: stdout | FileSink | OTLPHttpSink | MultiSink
      |
      +-- Optional: scenario_agent (pydantic-ai, gemini-2.5-flash-lite default)
                    analyses batch -> ScenarioAnalysis

Objective

Real GenAI traces are hard to get at scale for tooling development. This project generates a multi-service system (API gateway, RAG service, LLM inference, embedding, vector DB, payments, auth) with controllable fault scenarios injected at precise moments. You get:

  • OTLP-compatible trace JSON (spans with correct parent-child relationships, timing, attributes)
  • Structured logs correlated to traces by trace_id
  • Loki-compatible log push format
  • Anomaly signals strong enough to trigger real alerting rules
  • A pydantic-ai agent that analyses the batch and returns a ScenarioAnalysis with per-service signals

Architecture

Latency is sampled from a lognormal distribution derived from each service's p50/p99 profile. Error rates are per-service baselines, overridden by the active scenario.

Trace structure

Each generated trace represents one incoming request. The orchestrator always builds:

  1. api-gateway root span (HTTP SERVER)
  2. auth-service + postgres-auth sub-trace (every request)
  3. RAG path (~50% of requests): embed-service -> vector-db -> llm-gemini (+ 25% chance of a tool or MCP tool span as a child of the LLM span)
  4. Payments path (~40% of requests): payments-service -> postgres-payments + kafka
  5. Agentic path (~25% of requests): workflow-orchestrator -> plan -> memory-service (search) -> agent-service -> llm-gemini (chat) + 1-3 tool spans -> memory-service (upsert)

Approximately 15% of requests traverse both the RAG and payments paths.

Scenario engine

Scenarios are time-bounded fault injectors. Each scenario defines a start_offset_s, end_offset_s, apply(registry) callable, and recover(registry) callable. The engine ticks once per virtual second of generated time and transitions scenarios through PENDING -> ACTIVE -> DONE.

Fault propagation: when a downstream service is degraded, its immediate upstream callers inherit 30% of the error rate increase and 50% of the latency multiplier (one hop only, not transitive).

stateDiagram-v2
    [*] --> PENDING
    PENDING --> ACTIVE : elapsed >= start_offset_s<br>(apply called)
    ACTIVE --> DONE : elapsed >= end_offset_s<br>(recover called)
    DONE --> [*]

The data generator itself has no API key requirement. An API key is only needed when running --analyse without --mock. The default model is gemini-2.5-flash-lite (requires GEMINI_API_KEY). Set GOD_AGENT_MODEL to a Claude model and provide ANTHROPIC_API_KEY if you prefer that.

Installation

From the repo root:

make install

Or via clone & uv

git clone <repo-url>
cd genai-observability-data/src/god
uv sync --all-extras

This creates .venv/ and installs all runtime and dev dependencies.

Configuration

Settings are read from environment variables or a .env file placed in src/god/ (the working directory when the package runs).

Create your .env:

cp src/god/.env.example src/god/.env   # if the example exists
# or create manually:
cat > src/god/.env <<'EOF'
GEMINI_API_KEY=AIza...
GOD_MOCK_MODE=false
EOF

All settings

The default model is gemini-2.5-flash-lite. To switch to Claude, set GOD_AGENT_MODEL=claude-haiku-4-5-20251001 and provide ANTHROPIC_API_KEY. Model names can be bare (gemini-2.5-flash-lite) or provider-prefixed (google:gemini-2.5-flash-lite, anthropic:claude-haiku-4-5-20251001, openai:gpt-4o-mini).

No Elasticsearch or Redis keys are used by this project.

Root CLI (god-cli)

The repo root ships a standalone god-cli script that wraps the package with a Rich terminal UI. It requires no installation beyond the existing uv environment - just run it from the repo root.

# From the repo root (no cd required)
./god-cli --help
./god-cli --list-scenarios
./god-cli -n 50
./god-cli -n 500 --scenario cascading_failure -o ./output --format otlp_traces otlp_logs logfmt
./god-cli -n 200 --scenario llm_degradation --analyse

The script resolves src/god via sys.path automatically, so it works without activating the venv or installing the package as an entry point.

What the root CLI adds over python -m god

Feature python -m god ./god-cli
Output Plain stderr progress Rich panels, progress bar, colour
--help argparse default Formatted table with grouped options
--list-scenarios Plain text Rich table with tags and descriptions
Analysis output Plain print Severity-coloured anomaly signal panel
Run config Inline log line Pre-run configuration panel
gen-scenario subcommand Not available Batch all or one scenario into output/<scenario>/

The underlying generation logic, all flags, and all defaults are identical. Use ./god-cli for interactive terminal sessions; use python -m god (or the god entry point) in scripts and CI.

gen-scenario subcommand

god-cli adds a gen-scenario subcommand that runs one or all presets, writing each to its own subdirectory under --output (default ./output/). Multiple scenarios are run concurrently.

# Generate every preset into ./output/<scenario-name>/
./god-cli gen-scenario all

# One scenario, 200 traces, deterministic
./god-cli gen-scenario cascading_failure --traces 200 --seed 42

# Stream a scenario to an OTLP collector (disable mock when using a real model)
./god-cli gen-scenario rag_meltdown --otlp http://localhost:4318 --no-mock

usage: god-cli gen-scenario [SCENARIO] [--traces N] [--rate N]
                             [--format FMT ...] [--output DIR]
                             [--seed N] [--otlp URL] [--otlp-header KEY=VALUE]
                             [--compress] [--no-mock] [--quiet]

SCENARIO can be any preset name or all. Mock mode is on by default; pass --no-mock when you have an API key and want real analysis.

Quiet / pipe mode

--quiet (-q) suppresses all Rich output to stderr. Stdout stays clean data, suitable for piping:

./god-cli -n 1000 -q | grep "level=ERROR" | wc -l

How fault injection works

Each scenario is a ScenarioSpec (validated Pydantic config) paired with a ScenarioHandler (stateless fault logic). The ScenarioEngine ticks once per virtual second and drives each Scenario through its state machine.

stateDiagram-v2
    [*] --> PENDING
    PENDING --> ACTIVE : elapsed >= start_offset_s<br>(handler.apply called)
    ACTIVE --> RECOVERING : elapsed >= end_offset_s<br>(handler.recover called)
    RECOVERING --> DONE
    DONE --> [*]
flowchart TD
    A["ScenarioEngine.tick(elapsed_s)"] --> B{state?}
    B -->|PENDING, elapsed >= start| C["handler.apply(registry, spec)<br>set error_rate + latency overrides"]
    B -->|ACTIVE, elapsed >= end| D["handler.recover(registry, spec)<br>clear overrides"]
    C --> E["propagate_fault<br>30% err bleed to callers<br>50% latency bleed to callers"]
    D --> F["direct clear only<br>no transitive recovery"]

The token_budget_breach scenario is special: it sets _error_rate_override = 0.0 (suppressing baseline errors entirely). The truncation signal comes from a separate 5% random chance in build_inference_span, independent of the error rate.

Running tests

All tests are in src/god/tests/. The test suite requires no API keys or running services.

# From src/god/
uv run pytest

# With coverage
uv run pytest --cov=. --cov-report=term-missing

# Single module
uv run pytest tests/test_generators.py -v

# Via make
make test           # full suite with coverage
make test-unit      # alias

pytest.ini_options are configured in src/god/pyproject.toml:

  • asyncio_mode = "auto" - all async test functions run automatically (no @pytest.mark.asyncio)
  • pythonpath = [".."] - imports resolve as from god.models import ...
  • addopts = "-v --tb=short"

Test patterns

  • All LLM calls use the autouse fixture in test_agent.py that calls activate_mock_mode() / deactivate_mock_mode() around each test. No ALLOW_MODEL_REQUESTS guard is needed separately.
  • Deterministic generation: pass rng_seed=42 (or any int) to generate_dataset to get identical output on every run. Omit to get non-deterministic output.
  • Mock mode can be tested at the CLI level: GOD_MOCK_MODE=true uv run python -m god -n 5

Evaluation / analysis agent

The optional --analyse flag runs a pydantic-ai agent against the generated batch. The agent returns a ScenarioAnalysis with structured anomaly signals.

@dataclass
class AnomalySignal:
    service: str
    signal_type: str   # error_spike | latency_spike | token_truncation | tool_failure
    severity: str      # low | medium | high | critical

@dataclass
class ScenarioAnalysis:
    active_scenarios: list[str]
    anomaly_signals: list[AnomalySignal]
    error_rate: float
    p99_latency_ms: float
    recommended_action: str
    summary: str

The agent is invoked with a pre-computed summary (total spans, error rate, p99 latency, per-service error counts, token truncations, tool failures). It uses gemini-2.5-flash-lite by default (no fallback configured).

Running without an API key

Pass --mock to activate a deterministic FunctionModel that replicates the analysis logic locally. Mock mode is on by default (GOD_MOCK_MODE=true).

uv run python -m god -n 200 --scenario cascading_failure --analyse

Model override

Model names can be bare or provider-prefixed. Bare names are normalised automatically.

# Gemini (default)
uv run python -m god -n 200 --analyse --agent-model gemini-2.5-flash-lite

# Claude
uv run python -m god -n 200 --analyse --agent-model claude-haiku-4-5-20251001

# Via .env
GOD_AGENT_MODEL=anthropic:claude-haiku-4-5-20251001

Supported provider prefixes: google:, anthropic:, openai:. The provider prefix determines which API key is used (GEMINI_API_KEY, ANTHROPIC_API_KEY, or OPENAI_API_KEY).

Extending

Adding a new scenario

Scenarios are now split across three files in src/god/scenarios/:

  • _handlers.py - stateless fault logic (subclass ScenarioHandler, register with register_handler)
  • _registry.py - factory functions and SCENARIO_PRESETS dict
  • __init__.py - re-exports (add your new symbols here)

For simple faults the built-in SimplePropagateHandler is sufficient - just add a factory function in _registry.py and a preset entry in SCENARIO_PRESETS:

# src/god/scenarios/_registry.py
from god.scenarios._base import Scenario, ScenarioSpec
from god.scenarios._handlers import build_handler

def my_embed_overload(
    target: str = "embed-service",
    start_s: float = 30,
    duration_s: float = 150,
    error_rate: float = 0.3,
    latency_multiplier: float = 4.0,
) -> Scenario:
    return _make(ScenarioSpec(
        name="embed_overload",
        handler_type="simple_propagate",
        description=f"Embedding saturation on {target}: latency x{latency_multiplier}",
        start_offset_s=start_s,
        end_offset_s=start_s + duration_s,
        target=target,
        error_rate=error_rate,
        latency_multiplier=latency_multiplier,
        tags=["genai", "embed", "latency"],
    ))

SCENARIO_PRESETS["embed_overload"] = lambda: [my_embed_overload()]

For custom recovery logic, subclass ScenarioHandler in _handlers.py and register it:

# src/god/scenarios/_handlers.py
from god.scenarios._base import ScenarioSpec
from god.services import ServiceRegistry

class MyHandler(ScenarioHandler):
    def apply(self, registry: ServiceRegistry, spec: ScenarioSpec) -> None:
        registry.propagate_fault(spec.target, error_rate=spec.error_rate,
                                 latency_multiplier=spec.latency_multiplier)

    def recover(self, registry: ServiceRegistry, spec: ScenarioSpec) -> None:
        svc = registry.get(spec.target)
        svc._error_rate_override = None
        svc._latency_multiplier = 1.0

register_handler("my_handler", MyHandler)

Then use handler_type="my_handler" in your ScenarioSpec.

Rate limiting

The god HTTP client uses a two-layer rate-limiting strategy for outbound LLM and embedding calls: a per-operation token bucket (proactive throughput cap) and a concurrency semaphore (in-flight cap). 429 responses feed back into the token bucket to self-throttle under sustained upstream pressure.

See RATE_LIMITING.md for full configuration reference, tuning guidance, and known limitations.

Gotchas

  1. gen-otlp requires an API key (or mock mode). The make target does not set GOD_MOCK_MODE=true unlike gen, gen-files, and gen-fixtures. If you have not set GEMINI_API_KEY (or the relevant key for your chosen model) and are not in mock mode, the analysis agent will fail on --analyse. Pure generation without --analyse works fine without any API key. The default model is gemini-2.5-flash-lite; set GEMINI_API_KEY rather than ANTHROPIC_API_KEY unless you have set GOD_AGENT_MODEL to a Claude model (claude-haiku-4-5-20251001).

  2. Seed only partially controls randomness. A few choices inside the generators (HTTP method selection, some error type strings) use random.choice from the stdlib without seeding. For fully reproducible output, call random.seed(n) yourself before invoking generate_dataset.

  3. gen_ai.server.time_to_first_token is in seconds (OTel spec); gen_ai.server.ttft_ms is a non-standard convenience attribute in milliseconds emitted alongside it. Do not treat them as duplicates when writing dashboards.

  4. Token budget breach suppresses baseline errors. _error_rate_override = 0.0 means the service emits zero hard errors during that scenario window. The anomaly signal is purely in finish_reason=length spans, not in span status.

  5. OTLPHttpSink is synchronous. It uses urllib.request, not httpx. Large batches will block the main thread. Use a small --batch-size if this is a concern.

  6. Grafana dashboards are auto-provisioned from infra/grafana/dashboards/ on container start. Edits in the UI are ephemeral unless allowUiUpdates: true in the provisioning config (it is).

  7. int attribute values are serialised as strings in OTLP JSON per the OTLP spec: {"intValue": "1234"}. Some downstream consumers may need this handled explicitly.

  8. The tasks/ refactor plan describes flattening src/god/god/ -> src/god/. The file system already reflects the flat layout. If you encounter import errors referencing a double-nested path, the plan is stale.
